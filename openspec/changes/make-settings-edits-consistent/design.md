# Design

## Context

See [proposal.md](proposal.md). `SettingsWindowViewModel` loads a separate mutable `Settings` object, but keeps only `_lastAppliedTheme` as a restore point. Theme property notifications update `ThemeManager` before saving; nonappearance settings are normally applied by `AppController` after `SettingsApplied`. `ApplyAsync` changes Windows auto-start before `SaveAsync`, while `WindowsAutoStartService` swallows registration errors. `JsonSettingsProvider` writes directly to the settings file, and the controller's `async void` apply handler cannot report completion or failure to Settings. Theme reset also changes `ThemeService.CurrentTheme` immediately.

## Goals / Non-Goals

**Goals:** One full-settings restore point and one commit result; no save or nonappearance runtime side effect from tab navigation; reliable preview rollback; visible errors; a prior settings file that survives a failed write.

**Non-Goals:** OI-24 control restyling, new theme fields, changing the current immediate appearance preview default, previewing nonappearance settings, or adding OI-21's optional immediate-change toggle. Theme export and opening the repository remain explicit external actions, not Settings commits.

## Decisions

1. **Treat loading as a result, not merely a completed task.** A missing settings file may supply defaults. An existing file that cannot be read or parsed must produce a load error instead of the provider's current silent default fallback. Startup stops activation and opens Settings for retry; Settings remains non-editable and cannot commit until a retry succeeds. The original file is never overwritten by that fallback. On successful load, clone the full persisted state, including `Theme` and device identity, into a separate draft and restore point. Read the actual Windows auto-start registration separately. The toggle displays the saved value, not the observed registry value; a mismatch warning states that Apply or OK will reconcile registration to the saved candidate. Cancel leaves the mismatch untouched. This makes the saved setting authoritative without silently turning an unrelated edit into a toggle edit.
2. **Centralize commit and discard in the view model.** One awaited commit routine validates every draft-only input, builds a candidate without mutating the restore snapshot, and returns a typed success, ordinary failure, or recovery-required result. Apply and OK call it; OK closes only on success. After a successful commit, deep-copy the candidate into the restore snapshot and clear the preview-dirty state. Cancel and title-bar close share one idempotent discard path that restores the last committed theme in `ThemeManager` and resets any draft-only global theme service state. While a commit runs, disable Cancel and reject `Closing` requests without queuing them; a successful OK closes after the result, while Apply or a failure leaves the window open for a fresh close request. This prevents disposal or preview restoration from racing a commit.
3. **Keep previews limited and reversible.** Existing theme edits, preset selection, import, and reset still preview through `ThemeManager`, but cannot persist until commit. Reset uses a cloned built-in Dark theme for the draft instead of mutating `ThemeService.CurrentTheme`. Nonappearance values, including widget scale, opacity, compact mode, reminders, logging, hotkeys, and polling interval, remain draft-only until commit. The preview scope is explicit so a future immediate-change option can be added without changing commit semantics.
4. **Use a recoverable compensating transaction.** Give the settings provider a transaction-capable path that writes a same-directory candidate file, preserves the previous file (or records its absence), and records a small pending-commit journal with the previous Windows Run command and value kind before atomically replacing the settings file. Keep ordinary `SaveAsync` atomic as well. The coordinator then reconciles auto-start and awaits App-owned runtime activation instead of the fire-and-forget `SettingsApplied` event. Only after all three stages succeed may it remove the journal and advance the restore point. A failed candidate write leaves the prior file intact. A later failure triggers restoration of the previous file, exact registry value, and runtime state in reverse order. The Windows auto-start service must report failure rather than swallow it; its Core interface and Linux stub stay aligned without implementing Linux registration.
5. **Make incomplete restoration an explicit state.** If compensation succeeds, report an ordinary failed commit and retain the draft for retry. If any compensation step fails, retain the prior-state file and pending journal, report `RecoveryRequired`, and block new commits. Offer a Retry recovery action in Settings. Closing in this state warns that recovery is unfinished. On the next start, the settings provider detects the journal and refuses to load the candidate as committed; an App-owned coordinator retries file and Windows registration restoration before runtime activation. If recovery still fails, startup exposes the recovery-required error rather than silently loading defaults. The old snapshot remains the intended restore point, but the UI does not claim the disk, registry, or runtime state is known until recovery succeeds. Cross-resource atomicity is impossible, so the contract distinguishes this state from an ordinary failed commit.
6. **Show errors without losing edits.** Expose load, validation, commit, drift, and recovery messages in Settings. Preserve the polling-interval validation behavior, add checks for other editable values that can fail persistence or runtime activation, and clear obsolete errors when the relevant value changes or a commit succeeds. Keep Apply/OK available for retry after an ordinary failure, but unavailable during load failure, an active commit, or `RecoveryRequired`. Avoid a generic catch that only writes to the log.

## Risks / Trade-offs

- [A late or failed load overwrites user data] → Expose load failure, block editing/commit, and test delayed, unreadable, and malformed existing files separately from a missing file.
- [Failure between file, registry, and runtime steps] → Journal the previous state before replacement, compensate in reverse order, and block commits if recovery is incomplete.
- [The window closes while a commit is active] → Reject close requests until the awaited result arrives; test Apply and OK with delayed save and activation.
- [Saved auto-start and Windows registration differ] → Show the saved value and a reconciliation warning; test an unrelated Apply, Cancel, and failed reconciliation.
- [Auto-start service currently hides errors] → Change its contract and test denial/missing-key cases on Windows; keep the Linux stub aligned without implementing Linux auto-start (OI-06).
- [Async runtime reload currently uses `async void`] → Await an explicit result and prevent concurrent commits; test both success and thrown failure.
- [Theme reset mutates shared service state] → Build the draft from a clone and update shared theme state only on commit or restore.
- [Other OpenSpec changes also touch Settings] → Coordinate with `worklog-summary-breakdown` and `configure-activity-polling`, preserving Summary refresh and the polling interval's apply-only contract.

## Migration Plan

No settings-file migration is needed. Existing saved values and `.fttheme` files retain their schema. The journal and previous-state copy are sidecar recovery data, not new settings fields. On startup, resolve an unfinished journal before loading settings; never delete its previous-state copy as ordinary temporary-file cleanup. After a successful commit or recovery, remove the journal and abandoned candidate files. Reverting the executable preserves the JSON settings format, but an unfinished journal must be recovered with the new version before rollback so an older version does not mistake an uncommitted candidate for saved settings.
