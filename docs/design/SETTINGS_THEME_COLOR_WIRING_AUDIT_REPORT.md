# Theme color wiring audit

> Historical snapshot taken before the M03 widget material change. The widget-layer findings below describe the prior renderer; see `TOKEN_MAPPING.md` and the `restore-widget-frosted-glass` change for its replacement.

This is the original read-only audit, retained as a record of the defects and proposed work. The findings and line references below describe the app at the time of that audit. “Rendered” in that snapshot meant that project code assigned a brush to a control or style; it did not establish the Fluent template output.

## Current status (October 2026)

Desktop colors now use derived readable brushes across Settings, Worklog, color pickers, notifications, and their popups. The Appearance page uses Timer widget colors and Dialogs and notifications colors as peer cards, stacked at narrow widths. Tabs use an underline and an accent label; selected fields and Worklog rows use a matched fill/text pair. Widget source colors and the system tray menu retain their own rendering boundaries.

The [current contrast check](SETTINGS_THEME_COLOR_CONTRAST_CHECK.md) covers all seven presets and five difficult imports, including resolved Fluent template output and composited surfaces. The audit found concrete dropdown, calendar, translucent selection, and gray color-preview failures; their consumers now use readable derived brushes. The [verification record](../openspec/changes/archive/2026-10-08-optimize-theme-readability/verification.md) distinguishes automated checks and Windows bitmap captures from native interaction checks confirmed complete by the user on 2026-10-08.

Apply and OK commit the whole Settings draft; Cancel and title-bar close restore the last successful commit. Imported themes now retain a conditional Custom/Imported selection across reopening and restart, including imports named Dark. Source colors survive derivation and later factory tuning. See [palette tuning](../docs/versions/current/ThemePaletteTuning.md) and [OpenIssues.md](../docs/versions/current/OpenIssues.md); OI-21/OI-24/OI-29/OI-42 are completed following user confirmation of the combined native walkthrough on 2026-10-08, and optional nonappearance preview is OI-44.

## Diagnosis

- The Settings window sets `SettingsBackgroundBrush` and `PrimaryTextBrush`, but only section headers, marked labels, some notes, diagnostics, and the About version have explicit project text styles. Checkboxes, sliders, numeric inputs, text boxes, combo boxes, tabs, expander header text, and ordinary buttons rely substantially on Avalonia Fluent. A window foreground is inherited only where a control or template does not supply a stronger value. Local XAML values and template state styles can win over application styles. See [`SettingsWindow.axaml:14`](../src/FocusTimer.App/Views/SettingsWindow.axaml#L14), [`ControlStyles.axaml:61`](../src/FocusTimer.App/Styles/ControlStyles.axaml#L61), and [`App.axaml:6`](../src/FocusTimer.App/App.axaml#L6).
- `ButtonNormal` colors the widget action icons in both modes. `ThemeManager` also assigns `ActionPrimaryBrush = ButtonNormalBrush`, including the brush's `ButtonOpacity`, but **no Settings control consumes `ActionPrimaryBrush` today**. This is a latent semantic coupling, not proof that changing `ButtonNormal` recolors the current Settings buttons. `AccentPrimary` follows a separate path into focus rings, swatch borders, accordion borders, tab-selected resource, and Fluent accent keys. See [`ThemeManager.cs:83`](../src/FocusTimer.App/Services/ThemeManager.cs#L83), [`ThemeManager.cs:119`](../src/FocusTimer.App/Services/ThemeManager.cs#L119), and [`ThemeManager.cs:126`](../src/FocusTimer.App/Services/ThemeManager.cs#L126).
- `TabSelectedBackground` is serialized and present in every built-in theme, yet `TabSelectedBackgroundColor` is filled from `AccentPrimary`. None of the project tab brushes is assigned to a tab selector. See [`Theme.cs:442`](../src/FocusTimer.Core/Models/Theme.cs#L442), [`ThemeManager.cs:119`](../src/FocusTimer.App/Services/ThemeManager.cs#L119), and [`ThemeResources.axaml:158`](../src/FocusTimer.App/Styles/ThemeResources.axaml#L158).
- The visible tray menu is a native `NativeMenu` constructed in code. The XAML tray declaration is commented out; no widget `ContextMenu` is attached. The `ContextMenu` style therefore does not color the menu users currently open. See [`App.axaml.cs:65`](../src/FocusTimer.App/App.axaml.cs#L65), [`App.axaml:14`](../src/FocusTimer.App/App.axaml#L14), [`TrayStateController.cs:90`](../src/FocusTimer.App/Services/TrayStateController.cs#L90), and [`ControlStyles.axaml:189`](../src/FocusTimer.App/Styles/ControlStyles.axaml#L189).

## Widget opacity and menus

Full and compact modes use the same window shell and `timer-text` style. Full mode has four action icons and the project field; compact mode has play/pause and expand. The minimize icon is in the parent window. The action icons keep `ButtonNormalBrush` while hover and pressed backgrounds come from `TitleBarButtonHover/PressedBrush`. Focus uses `FocusRingBrush`. See [`FullModeView.axaml:23`](../src/FocusTimer.App/Views/FullModeView.axaml#L23), [`CompactModeView.axaml:18`](../src/FocusTimer.App/Views/CompactModeView.axaml#L18), [`TimerWidgetWindow.axaml:56`](../src/FocusTimer.App/Views/TimerWidgetWindow.axaml#L56), and [`ControlStyles.axaml:9`](../src/FocusTimer.App/Styles/ControlStyles.axaml#L9). `ColorOpacityToBrushConverter` and `TimerWidgetViewModel.BackgroundBrush` exist but are not bound by the current widget XAML.

`WindowBackgroundBrush` already has `BackgroundOpacity`, while its panel has `BackgroundOpacity × WidgetOpacity`, and the window itself has `WidgetOpacity`. The timer brush has `TimerOpacity` and its clock layer has `TimerOpacity × WidgetOpacity`; button brushes and controls layers repeat that pattern. Embedded ARGB alpha adds another factor. The rear shell separately uses `WidgetBaseOpacity × WidgetOpacity`, so zero panel opacity does not imply a transparent widget. When background opacity is zero, `ThemeManager` replaces `WindowBackgroundBrush` with transparent but leaves `WindowBackgroundColor` at its prior value. The composite output, including material fallback, needs a running Windows check. See [`ThemeManager.cs:54`](../src/FocusTimer.App/Services/ThemeManager.cs#L54), [`TimerWidgetViewModel.cs:326`](../src/FocusTimer.App/ViewModels/TimerWidgetViewModel.cs#L326), and [`TimerWidgetWindow.axaml:21`](../src/FocusTimer.App/Views/TimerWidgetWindow.axaml#L21).

The tray menu has native, OS-controlled surface, text, hover, disabled, separator, and focus colors. No theme property updates them. Windows draws it as a system menu; Avalonia requires `NativeMenu` for `TrayIcon.Menu`. An Avalonia `ContextMenu` could be themed if one were attached to a widget control, but none is. Keep the native tray menu for platform behavior, keyboard access, and lower maintenance. A custom app popup could follow the palette, but would need separate positioning near the tray, dismissal, focus, keyboard navigation, accessibility, and cross-platform handling. See the [Avalonia TrayIcon guide](https://docs.avaloniaui.net/controls/navigation/trayicon) and [Windows tray guide](https://docs.avaloniaui.net/docs/platform-specific-guides/windows).

## Proposed semantic roles

| Area | Roles and backing values | Distinct role needed |
|---|---|---|
| Settings surfaces and text | `SettingsSurface ← SettingsBackground`; `SettingsHeader ← SettingsSectionHeader`; `SettingsLabel ← SettingsLabelText`; `SettingsBody ← PrimaryText`; `SettingsMuted ← SecondaryText` | Split Settings text from widget secondary text if users edit them independently; define accordion surface/header/hover/border/text separately from input and global accent. |
| Settings fields, tabs, focus | Field surface/border/text/focus ← `InputBackground`/`InputBorder`/`InputText`/`InputFocusBorder`; each tab state ← its matching `Tab*` property | Explicit checkbox, slider, focus, read-only, disabled, and error-state roles where existing values do not express the intended contrast. |
| Settings actions | Normal, hover, pressed, disabled, and foreground | New Settings action palette. Do not source `ActionPrimaryBrush` from widget `ButtonNormalBrush`. |
| Widget shell and clock | Shell/base/border ← `WindowBackground`, `WidgetBaseOpacity`, `WindowBorder`; clock text ← `TimerText`; backdrop only if `TimerBackground` is intended to render | Separate minimize/icon secondary color from Settings muted text if needed; single opacity owner per layer. |
| Widget controls and field | Icon normal/hover/pressed/disabled ← `Button*`; project field ← `ProjectTag*`; focus ← intentional focus role | Widget control hover/pressed backgrounds and focus may share deliberate accent values, but should not inherit Settings action colors. |
| Themeable Avalonia menu, if introduced | `MenuSurface`, `MenuText`, `MenuHover`, `MenuDisabled`, `MenuBorder`, `MenuFocus` | Distinct menu roles. The current native tray menu remains system-controlled. |

## Live changes and contrast

Editing a color, selecting a preset, importing, or resetting changes `Settings.Theme`, and the Settings view model calls `ThemeManager.ApplyTheme` on theme property or replacement notifications. Apply saves and triggers a settings reload; OK does the same and closes after a successful save. Cancel only closes. It does not restore the previous app-wide palette, so a canceled color preview can remain visible until another theme is applied. The Settings view model loads a separate settings instance; resource-backed widget colors may update before widget opacity and other settings, which are reloaded on Apply. See [`SettingsWindowViewModel.cs:390`](../src/FocusTimer.App/ViewModels/SettingsWindowViewModel.cs#L390), [`SettingsWindowViewModel.cs:425`](../src/FocusTimer.App/ViewModels/SettingsWindowViewModel.cs#L425), [`SettingsWindowViewModel.cs:640`](../src/FocusTimer.App/ViewModels/SettingsWindowViewModel.cs#L640), [`SettingsWindow.axaml.cs:51`](../src/FocusTimer.App/Views/SettingsWindow.axaml.cs#L51), and [`AppController.cs:442`](../src/FocusTimer.App/Services/AppController.cs#L442). The native menu has no app-color preview.

All seven built-in themes set palette values, and existing `ThemeManagerTests` verify resource creation and a file round trip. They do not measure rendered contrast. Specific risks are Light palette colors under the system-driven Fluent theme variant, High Contrast selected-tab text whose intended black value is not wired to a tab state, translucent widget button colors after repeated opacity, and Fluent foregrounds over changed Settings surfaces. `.fttheme` import validation checks only four nonempty strings, not every color's syntax or contrast; a parse failure can leave an older resource value. A custom file can therefore import yet yield unreadable combinations. No contrast ratio is claimed here. See [`ThemeService.cs:105`](../src/FocusTimer.Core/Services/ThemeService.cs#L105), [`ThemeService.cs:166`](../src/FocusTimer.Core/Services/ThemeService.cs#L166), [`ThemeService.cs:401`](../src/FocusTimer.Core/Services/ThemeService.cs#L401), [`ThemeManager.cs:191`](../src/FocusTimer.App/Services/ThemeManager.cs#L191), and [`ThemeManagerTests.cs:9`](../tests/FocusTimer.App.Tests/ThemeManagerTests.cs#L9).

## Color-wiring plan

1. Correct `TabSelectedBackground` and `InputFocusBorder` source assignments. Add focused resource tests for each tab property and for parse failures.
2. Give Settings text, fields, tabs, accordions, buttons, and focus states explicit semantic brushes and selectors. Inspect Fluent template value sources before finalizing checkbox, slider, tab, and expander styling. Preserve layout and geometry.
3. Source Settings actions independently of widget `Button*` colors. Wire widget icon hover, pressed, disabled, minimize, and focus states in both modes.
4. Apply each widget opacity at one intended layer; decide whether unused exposed colors should gain consumers or leave the editor. Keep the native menu system-controlled.
5. Make Cancel restore unsaved palette and opacity previews consistently; validate all imported colors and relevant foreground/background pairs before application.

## Focused verification

- In General, Logging, Appearance, About, and Hotkeys, inspect ordinary and marked text, every field type, tab states, accordions, checkboxes, sliders, buttons, tooltip, read-only/disabled states, and keyboard focus. Use Avalonia DevTools to identify the winning Fluent or project value source. [Avalonia resource lookup](https://docs.avaloniaui.net/docs/app-development/resources) and [style precedence](https://docs.avaloniaui.net/docs/styling/style-best-practices) explain why a resource or selector can lose.
- Repeat with Dark, Light, Monokai, Solarized Dark, Nord, Dracula, High Contrast, and an imported `.fttheme`; check foreground/background pairs and focus indicators with measured contrast rather than palette names.
- Check full and compact widget clocks, shell, borders, icons, minimize, full-mode project field, hover, pressed, disabled, and keyboard focus at full, partial, and zero layer opacity. Observe live color edits separately from Apply.
- On Windows, open the actual tray menu by right-clicking the tray icon; verify its commands, native colors, keyboard behavior, and lack of app-palette response. Right-click the widget to confirm no app menu is attached.
- Preview a color, Cancel, reopen, Apply, and OK; compare Settings, both widget modes, and the tray menu at each point. Repeat after import and restart.
