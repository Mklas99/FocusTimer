# FocusTimer - Next-Version Open Issues

> Working backlog for the next version. It lists only issues that still need work; completed issues keep their ID and are listed in the version snapshots: [v0.1](../v0.1/OpenIssues.md), [v0.2](../v0.2/OpenIssues.md). Manual checks left open by archived changes are in [OpenTasks.md](../../OpenTasks.md); the order of work is in [Planning.md](Planning.md).

|---|---|---|---|---|
| OI-01 | Global Hotkeys | Hotkeys cannot be edited in Settings. | Open | Registration and dispatch work; only capture, validation, and saving are missing. |
| OI-02 | System Tray | The tray menu has no quick actions such as project switching. | Open | Define the smallest useful action set before implementation. |
| OI-03 | Widget UI | Window position and size are not persisted. | Open | No window-bounds settings exist; restoration must protect against off-screen placement. M01 only supplied canonical base dimensions and spacing. |
| OI-04 | Settings / Reporting | There is no breakdown or user-facing report by app or project. | Partially delivered | F-02 adds a breakdown by application or project, built on a reusable summary service. F-03 moves it into the tray-opened Worklog window, adds a by-window grouping, and lets the user pick a single day (OI-33). Still open: broader time ranges, filter controls, and day grouping. |
| OI-05 | Diagnostics | Settings has no action to open the logs folder. | Open | Logging itself is already available. |
| OI-06 | Cross-platform | Linux implementations remain incomplete. | Open | Linux parity needs a platform target and real implementations for platform services. |
| OI-08 | Data features | Project tagging is manual only. | Implemented; manual Windows walkthrough open | Rules-based application/window pattern mapping is implemented by OpenSpec change `rule-based-projects`, archived with one check still open: the manual Windows walkthrough (add a rule for an IDE and confirm Entries and Timeline relabel live and the by-project summary changes after refresh, confirm a session project wins, remove the rule and confirm reversion). F-02 introduced an `IProjectResolver` seam so rule-based detection can replace the stored-tag resolver without changing summaries. Ordered pattern-to-project rules (Settings → Logging) resolved at read time (retroactive, stored entries untouched), explicit session/editor projects win, editor in Settings. |
| OI-09 | Persistence | CSV is the only storage backend. | Open - investigate | Evaluate actual reporting and editing needs before committing to a storage migration. |
| OI-10 | Focus modes | Pomodoro work/break automation is absent. | Open | Separate product decision from existing break reminders. |
| OI-11 | Focus modes | Break and resume events have no optional sound cues. | Open | Needs an accessibility-conscious enable/disable setting. |
| OI-12 | Reporting | Worklog exports and reusable export presets are absent. | Open | Existing export functionality applies only to themes. |
| OI-14 | Activity tracking | Foreground-window polling and segmentation cannot be configured. | Partial | `configure-activity-polling` implements Developer Options polling of 1–60 seconds, default 10, with live application and safe capture scheduling. Segmentation rules are implemented by OpenSpec change `segmentation-rules` (Developer Options list that stops title changes from splitting segments in matching applications; minimum-duration merging deferred), archived with its manual Windows walkthrough still open (add a browser rule, switch tabs and confirm one entry in Entries and Timeline, switch application and confirm a split); the polling change is archived too. |
| OI-16 | Distribution | Installer size and release variants. | Implemented; install validation open | Clean build: self-contained MSI 36.04 MiB, .NET-aware setup 13.10 MiB, compressed portable EXE 46.34 MiB. The setup checks for .NET 8 and downloads the verified runtime only when missing; the setup's detection/download path is untested (no environment without .NET 8 preinstalled set up yet). The build also produces a direct framework-dependent MSI (12.16 MiB), still built as the setup's chained payload but no longer published as a release asset — it only served a managed-deployment scenario this personal project doesn't have. Trimming currently fails on ThemeService JSON serialization warnings (IL2026); verify install, upgrade, runtime download, and same-version variant switching before release. |
| OI-17 | Performance | Broader resource costs need measurement and optimization. | Partial | `configure-activity-polling` implements a bounded Windows process-lifetime cache and configurable sampling. [Release evidence](../../performance/ActivityPollingPerformance.md) confirms component lookup reduction; whole-app savings are unmeasured. Settings reads and worklog writes remain separate investigation areas. |
| OI-20 | Data evolution | There is no agreed general strategy for migrating persistent worklog formats between releases. | Investigate | Research installer versus first-run migration, portable upgrades, backups, idempotent recovery, rollback, and eventual removal of legacy migration code. This is intentionally outside the development-only worklog-foundation change. F-03 adds the `manual` capture source (no schema version change); an older build reads such rows as malformed records (a warning) instead of losing them, and F-03 also changes the tracker to close segments at 23:59:59, so older files may contain entries that end exactly at midnight, which stay readable and editable. |
| OI-23 | Reporting | Users cannot see recorded work as a chronological timeline. | Partially delivered | The Worklog window's Timeline tab draws one day along a time axis in start order, with a vertical zoom (Ctrl + mouse wheel, Ctrl + plus/minus/0, or buttons) that is remembered between runs in `worklog-view.json` beside the settings file, and a Group by switch (all together, by application, by project, by window) that shows one column per group with its total time. Overlapping entries sit side by side, gaps stay empty, and manual entries are marked by label and outline (not color alone). It shows the same read warnings as the Entries tab. Ranges beyond one day remain open. The F-03 Windows walkthrough was confirmed complete by the user on 2026-10-08; OpenSpec change archived on 2026-10-08. |
| OI-26 | Developer workflow | VS Code F5/Start can launch a different build than the documented Host `win-x64` run command, showing stale UI. | Open | Identify the selected launch configuration and align the build and executable paths with `dotnet run --project src/FocusTimer.Host --runtime win-x64`. Local `.vscode` changes are ignored by Git, so a reproducible repository setup is still needed. |
| OI-27 | Settings persistence | A valid older settings file without `deviceId` loses its loaded preferences for the current run if the identity migration write fails. | Open | Settings writes now use same-directory atomic replacement, protecting the prior JSON. The migration still throws on a denied write; return the parsed settings with a process-stable ID and log the failure, then add a denied-write regression case. |
| OI-30 | Developer diagnostics | Live application logs cannot be read inside Settings. | Open | Show current application diagnostic logs in Settings when Developer mode is enabled, with new messages appearing while the window is open. Keep this separate from worklog records and the OI-05 logs-folder action. Define bounded history, scrolling, and refresh behavior so continuous logging does not block the UI. |
| OI-32 | Developer activity tracking | Applications cannot be excluded from worklog recording. | Implemented; manual Windows walkthrough open | In Developer mode, let the user configure applications whose activity must not be recorded. Apply exclusions during capture rather than merely hiding rows in reports; preserve existing worklogs. Define application matching, persistence through Apply/OK/Cancel, and treatment of excluded intervals so their time is not attributed to the next recorded application. Implemented by OpenSpec change `app-exclusions`, archived with one check still open: the manual Windows walkthrough (exclude an app by name, confirm the Timeline shows a gap and the next app starts fresh, restart and confirm the rules persist). Automated tests pass on Linux only. Built from the Developer Options editor, tracker exclusion state, and `WindowMatchRule` matcher: rules match application and/or title by case-insensitive wildcard, excluded time leaves a gap, and the matcher is shared with OI-14 and OI-08. |
| OI-34 | Error handling / user feedback | Error handling and user-facing errors and warnings have no consistent policy. | Open - investigate | Explore how failures are propagated, logged, and displayed across startup, Settings, tracking, persistence, and reporting. Build on existing Settings retry/recovery and Summary read warnings. Decide severity, when to use inline messages or notifications, useful recovery actions, and duplicate-message handling. Keep detailed diagnostics available in Developer mode while giving users clear explanations, especially when recording or saving fails. |
| OI-36 | Developer activity tracking | Idle detection behavior cannot be configured. | Open | Add Developer mode settings for idle detection rules, including the threshold and an option to resume the timer automatically when an idle check detects activity again. Resume only an idle-triggered pause; preserve manual pauses and stopped timers. Define whether return-to-activity notifications still appear, retain the session/project context, and verify repeated idle/active transitions. Persist through Apply/OK and restore on Cancel. |
| OI-38 | Worklog inspection | Timeline entries cannot be bucketed into larger time groups. | Open | Add a way to bucket log rows in the Timeline for easier inspection of recorded activity. Define the bucket interval and how entries spanning bucket boundaries are displayed. |
| OI-39 | Worklog management | Choosing a project in the project field is slow and error-prone. | Open | Improve the project field dropdown so users can switch projects faster and select the intended project reliably. |
| OI-43 | Developer diagnostics | Developer Settings cannot trigger app actions for testing. | Open | Add Developer mode actions to trigger information, warning, error, and break-reminder notifications, including acknowledgement reminders. Use the real notification path so theme colors, dismissal timing, and configuration can be checked without waiting for events. Define other useful test actions explicitly and label simulated actions clearly; avoid changing saved settings or worklog records unless the action explicitly requires it. Coordinate with OI-34 and OI-41. |
| OI-44 | Settings / preview | Nonappearance settings cannot be previewed before Apply/OK. | Open - design | Explore an optional preview mode for eligible nonappearance settings. Define which runtime changes are safe and reversible, which remain commit-only, how preview failures are shown, and how Cancel/title-bar close restores the last successful Apply/OK. Preview must not persist edits or weaken the shared draft, validation, commit, and recovery model. Appearance preview remains immediate by default. Moved out of OI-21 so the visual redesign can be completed independently. |
